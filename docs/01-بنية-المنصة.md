# بنية المنصة — إدارة الخدمات الفنية

منذ update73 المنصة هي منصة **إدارة الخدمات الفنية** بأقسامها الثمانية (المشاريع، المرافق، الصيانة، الأمن والسلامة، الصيانة الطبية، التجهيزات الطبية، الخدمات العامة، تقنية المعلومات)؛ قسم المشاريع أحد أقسامها بوحداته التفصيلية القديمة، وبقية الأقسام تعمل عبر **المحرّك التشغيلي** المشترك (`ops`) وأدلة الحوكمة.

## التقنية

- **واجهة**: تطبيق صفحة واحدة بلا إطار عمل (Vanilla ES Modules) + موجّه بالـ hash (`#/route`). ملفات: `site/index.html`, `site/app.css`, `site/js/*.js`, `site/sw.js` (Service Worker للإشعارات)، `site/manifest.json` (PWA). أسماء ملفات JS بحروف صغيرة وشرطة سفلية فقط (شرط ختم الكاش في `deploy.yml`).
- **استضافة**: GitHub Pages (مجانية) على الدومين `ahc-tsd.com` (ملف `site/CNAME` يبقى في المستودع)، النشر تلقائي عبر GitHub Actions عند كل دفع إلى `main`.
- **قاعدة البيانات والمصادقة والتخزين**: Supabase (PostgreSQL + RLS + Storage + Edge Functions `push` و`ical`).
- **الإصدار**: يُحقن `site/config.js` وقت النشر بعنوان Supabase والمفتاح العام (anon) ومفتاح VAPID العام ورقم الإصدار (SHA)، وتُختم كل الاستيرادات بـ `?v=SHA` لكسر الكاش (و`index.html`/`r.html`/`b.html`/`fmr.html`)، ويظهر شريط «صدرت نسخة جديدة» تلقائياً.

## الأدوار

`admin` (مدير النظام — صالح)، `engineer` (مهندس مشاريع: ينشئ مشاريعه ويعدّلها فقط)، `viewer` (قراءة)، `finance` (تسجيل الصرف في المستخلصات فقط)، `clerk` (إداري: اطلاع + طباعة + رفع مستندات)، `facility` (مرافق وصيانة: متابعة الأنظمة وأعمال المرافق والصيانة والأمن والسلامة إن لم يُحدَّد قسمه)، `tech` (موظف قسم فني: يعمل على أعمال قسمه `profiles.unit`)، `requester` (مُبلّغ من المنشأة: يرفع الطلبات ويتابعها ويؤكد معالجتها ويقيّمها فقط؛ `profiles.facility_id` منشأته)، `pending`، `disabled`.
دوال DB: `my_role()`, `is_admin()`, `can_edit()`, `can_read()`, `can_docs()`, `is_finance()`, `can_fm()`, `fm_write()`, `my_unit()`, `ops_read()`, `ops_staff(unit)` (فريق القسم أو الإدارة)، `unit_members(unit)`. الصلاحيات مطبّقة في قاعدة البيانات (RLS + محفّزات حارسة) لا في الواجهة فقط. المستخدم لا يغيّر قسمه أو منشأته بنفسه (`profiles_guard`).
**قيد الأدوار** `profiles_role_check` يُعاد إنشاؤه في `0005` و`0013` و`0038` و`0042` في كل نشر؛ أي دور جديد يُضاف في الأربعة.

## المحرّك التشغيلي (ops) — كيف يعمل

- **`ops_kinds`** نوع العمل (النموذج): `unit` القسم، `proc` الإجراء الحاكم، `intake` (يظهر للجميع في مركز البلاغات أو لفرق الأقسام فقط)، `prio`، `fields` (حقول النموذج JSON)، `close_fields` (بيانات الإنجاز تُطلب عند «أُنجز/إغلاق»)، `gates` (اعتمادات أقسام أخرى قبل حالة معينة)، `checklist` (بنود إلزامية قبل «مكتمل»)، `effect` (closure/impair/shutdown/permit/accept — أثر على حالة الموقع). الأنواع الحالية: استقبال لكل قسم `mnt, bme, it, gen, saf, fac, med, prj, access`، ولفرق الأقسام `closure, permit, impair, shutdown, ppm, accept, recall, ceval`.
- **`ops_items`** العمل: `ref` (مثل MNT-26-00012)، الحالة `new → accepted → in_progress ⇄ on_hold → verify → done` أو `cancelled`، الأولوية `p1..p4` والمهلة `due_at` من R-17 (`ops_sla`)، `proc/step`، `assignee`، `requester`، `parent_id` (الإحالة بين الأقسام)، `fm_obs_id`، `project_id`، `location_id`، `asset_id`، `plan_id`، `data` (قيم الحقول، `gates`، `check`، `plan_check`)، `last_action*`، `rating/feedback`.
- **`ops_biu`** يفرض: الإجراء المتخذ مع كل تغيير حالة/خطوة/قسم؛ حدود صاحب الطلب (إلغاء الجديد، تأكيد أو رفض المعالجة، التقييم فقط)؛ الاعتمادات وقائمة التحقق (`ops_check_rules`)؛ لا تُكتب `data.gates` إلا عبر الدالة `ops_gate(id, key, note)` (لفريق قسم البوابة أو الإدارة)؛ إعادة التوجيه تأخذ نوع الاستقبال وإجراءه للقسم الجديد. **`ops_aiu`** يسجّل التغييرات في `ops_log` ويُشعر (kind `ops`)، ويكتب في سجل العمل الأب عند الإحالة واكتمالها. **`ops_effects`** يغيّر حالة الموقع (مغلق/مقيد/تشغيلي). **`ops_asset_fx`** يجعل الأصل «متعطلاً» عند بلاغ توقف ويعيده عند الإغلاق.
- **`fac_locations`** سجل المواقع والغرف (يديره فريق المرافق). **`assets`** سجل الأصول لكل قسم (يديره فريقه). **`ops_plans`** الأعمال المخططة الدورية، و`ops_generate()` يولّد أوامر العمل المستحقة (في كل نشر وفي الجدولة اليومية).
- **`ops_daily()`** الملخص الصباحي لكل قسم (متأخر، جديد لم يُستلم منذ يوم).

## قاعدة البيانات (الترحيلات بالترتيب، كلها idempotent وتُنفَّذ في كل نشر)

`0001`–`0035` (المشاريع ووحداتها، الإشعارات، التقويم، المقطوعية، الإجازات، الرسائل، السلاسل، العروض، المرفقات، الإشارات، الخريطة، الحوكمة) · `0036` دليلا المرافق والصيانة · `0037` الأمن والسلامة وإعادة الترقيم · `0038` متابعة أنظمة المنشآت ودور facility · `0039` استيراد جولة سبتمبر · `0040` متابعة الأنظمة (2): الإجراء المتخذ، الروابط العامة، `fm_daily` · `0041` أدلة الصيانة الطبية والتجهيزات الطبية والخدمات العامة وتقنية المعلومات · `0042` المحرّك التشغيلي (الأدوار tech/requester، `ops_kinds/items/log`، الصلاحيات، المحفّزات، `ops_daily`) · `0043` المواقع والغرف، البوابات وقوائم التحقق، الإغلاق/التصريح/تعطيل الحريق/الإيقاف المخطط · `0044` الأصول والأعمال المخططة و`ops_generate`، استلام الأجهزة والاستدعاءات والصلاحيات وتقييم المقاولين · `0045` بيانات الإنجاز لكل نوع وتصحيح بيانات مشروع مولد العيون.

قواعد مهمة: الترحيلات بلا معاملة واحدة لكل ملف، لذا يجب أن تكون قابلة لإعادة التشغيل (`if not exists`, `drop ... if exists`, `on conflict do nothing`، وتحديث البذور بشرط «لم يُعدَّل من الموقع» مثل `where gates = '[]'`). عند إعادة تعريف دالة في ترحيل لاحق (مثل `ops_biu` في 0043) يبقى التعريف الأحدث هو الساري لأن الترحيلات تُنفَّذ بالترتيب.

## المهام المجدولة (GitHub Actions)

- `deploy.yml`: عند كل دفع + جدولان يومياً (04:45 و12:30 UTC). الوظائف: الترحيلات → البذر والاستيراد → خطوة SQL في كل تشغيل (`notify_stale_projects`, `sync_schedule_progress`, `notify_late_milestones`, `notify_overdue_challenges`, `notify_leave_events`, `notify_scheduled_messages`, `ops_generate`) → الملخص اليومي في الجدولة (`daily_digest`، وصباحاً `fm_daily(7)` و`ops_daily()`) → سجل `logs/seed.txt` → نشر الموقع → Edge Functions (تفشل حالياً حتى تجديد السر `SUPABASE_ACCESS_TOKEN`).
- `backup.yml`: كل جمعة 02:00 UTC ويدوياً: pg_dump + Excel + JSON مشفّر → `ahc-backups/weekly/`.
